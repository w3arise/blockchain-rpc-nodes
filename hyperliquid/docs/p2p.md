# Hyperliquid P2P (non-validator)

How a non-validator finds peers, what the ports do, and what to expect when you look at connections. Setup steps are in [../README.md](../README.md).

## Connection model

A non-validator streams blocks from **one peer at a time**. Everything else is short request/response traffic.

| Traffic | Port | Lifetime |
| --- | --- | --- |
| Block / ABCI stream (outbound to one peer) | remote `4001` | Long-lived, until the peer drops or stalls |
| Gossip RPC: peer exchange, client-block range queries (inbound and outbound) | `4002` | Opens, answers, closes in well under a second |
| Other nodes streaming from this node (inbound) | `4001` | Long-lived while they stay connected |

Peering providers describe the same model: the node "keeps one peer connection that actually feeds it. If that peer is slow, your node is slow. If it drops, your node stops." ([Dwellir](https://www.dwellir.com/hyperliquid-peering))

When the stream peer drops, the node tries candidate peers one by one (roughly every 5s) until one accepts. Public peers often answer `Peer full`. Upstream only says startup "may take a while as the node navigates the network to find an appropriate peer to stream from."

Consequences:

- Sync is a sawtooth: steady catch-up while a peer streams, lag growth while the node looks for the next one.
- One `ESTABLISHED` stream connection is normal. It is not a missing setting.
- Open upstream issue: the node rotates only when the stream stops, not when it is slow. A peer that keeps delivering blocks below chain rate can pin the node behind the tip until restart ([hyperliquid-dex/node#156](https://github.com/hyperliquid-dex/node/issues/156)).

## Ports

- **4001 and 4002 (TCP)** must be reachable from the internet. Upstream: "Ports 4001 and 4002 are used for gossip and must be open to the public." Unreachable nodes are deprioritized by peers.
- **4000–4010** is the validator range ("currently only ports 4001-4006" are used). Non-validator docs do not list anything beyond 4001–4002. `hl-node` also listens on 4005 inside the container. This repo does not publish it.

## Gossip config (`override_gossip_config.json`)

Generated by `./override-gossip.sh` from `env.template` / `.env`. The binary reads only these peer keys:

| Key | Source | Effect |
| --- | --- | --- |
| `root_node_ips` | `RESERVED_PEER_IPS`, then `SEED_PEER_IPS`, then the `gossipRootIps` API. Only addresses whose TCP 4001 answers are kept. | Bootstrap candidates |
| `reserved_peer_ips` | `RESERVED_PEER_IPS` (reachable ones) | These IPs are always accepted for **inbound** connections, even when this node is full. It does **not** pin the outbound stream peer. |
| `n_gossip_peers` | `N_GOSSIP_PEERS` (8–100) | Gossip peer target |
| `try_new_peers` | fixed `true` | Discover peers beyond the roots |

The script drops the host's own public IP (`$HOST_DATADIR/override_public_ip_address`, written by `./configure.sh`), so one `RESERVED_PEER_IPS` list works on every host. Run `./configure.sh` before `./override-gossip.sh`.

To make two of your nodes back each other up, list both in `RESERVED_PEER_IPS` and deploy the same config to both. Each then always accepts the other, so neither gets `Peer full` from the other. For dedicated, allowlisted peers, see paid sentry peering ([QuickNode](https://www.quicknode.com/blog/hyperliquid-sentry-peering-explained), [Dwellir](https://www.dwellir.com/docs/hyperliquid/peering)).

## Initial state (ABCI) bootstrap

A node without local state downloads it from a peer on 4001: an ABCI state (about 1.2 GB) plus an EVM RocksDB checkpoint. Any synced peer with a free slot can serve it. It does not have to be a validator. Peers greet with `send_abci=true` only while the requesting node has no state.

Log lines while this works:

- `reading bytes for abci_stream recv greeting: N/TOTAL`
- `received rocksdb from tcp stream`
- then `visor_abci_state.json` appears under `hyperliquid_data/` and `/evm` answers.

`could not read abci state ... early eof` means the peer dropped mid-transfer. The node retries with another peer.

If the download completes and the node still restarts, check `$HOST_DATADIR/data/visor_child_stderr/`. `thread '<unknown>' has overflowed its stack` is fixed by `RUST_MIN_STACK` in `env.template`.

## Looking at connections

The node runs in its own Docker network namespace. Compose publishes 4001/4002 with iptables DNAT, so **`netstat` / `ss` on the host show none of the node's peer connections**. Look inside the container:

```bash
PID=$(docker inspect -f '{{.State.Pid}}' hyperliquid-node-1)
sudo nsenter -t "$PID" -n ss -tn     # or: docker exec hyperliquid-node-1 cat /proc/net/tcp
```

A single snapshot shows one or two sockets. Sample repeatedly (every 0.25s for 10s, for example) to see the short 4002 exchanges: many inbound connections from different peers in a few seconds is healthy.

On `LISTEN :4001`, a non-zero accept queue that grows (`Recv-Q` in `ss -ltn`, the `rx_queue` column in `/proc/net/tcp`) means `hl-node` is not accepting. Outside checks then time out on 4001 even though the port is open. That happens while the node has no loaded state.
